# 客户端网盘功能（对接 B/S「个人空间」自动同步）技术与业务分析

> 2026-10-14 · 基于 aif-desktop-client（Tauri 2）现状 + 51yunwei.com.cn 真实登录态 curl 实测（AIF zjb / DCP zjb 双会话）

---

## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| 可行性 | **可行**。B/S「个人空间」是 knowledge 模块的目录树 + FILE 型文章结构，文件的上传/下载/替换接口全链路已实测打通 |
| 核心映射 | 本地目录 ↔ subject（目录树）；本地文件 ↔ FILE 型 article（文件即文章） |
| 最大风险 | B/S **无内容 hash/ETag、无增量/断点续传、无批量元数据 API**——同步引擎只能靠 `size + updateTime` 弱比较，远端变更检测需全量拉树 |
| 建议路径 | P0 补测写接口（0.5d）→ P1 单向下载镜像（2~3d）→ P2 双向自动同步（4~6d）→ P3 打磨（3~5d） |
| 首版形态 | 「我的」设置里配一个本地目录 ↔ 「我的目录」subject 配对，托盘/迷你条显示同步状态，冲突保守处理 |

## 1. B/S「个人空间」实测结论（证据链）

### 1.1 产品形态

个人空间入口 `/{root}/knowledge/personal/view.htm`，属于 **knowledge（知识库）模块**，不是独立网盘模块。数据结构：

```
个人空间 (spaceId = PERSONAL_SPACE_<租户ID>)
└── subject 目录树（"我的目录"、"我的填报"、用户自建目录…）
    └── article 文章（叶子节点）
        ├── type=DOC / RICHTEXT / COLLEXCEL  ← 在线文档（正文在库里）
        └── type=FILE                        ← 附件型文档，文件本体在文件服务
```

- **文件即文章**：上传一个文件 = 在某 subject 下创建一篇 `type=FILE` 的 article，`title` 即文件名，文件本体通过文件服务存取（实测一篇 FILE 文章 9MB docx）。
- spaceId 为租户级固定值（zjb 两个产品下都是 `PERSONAL_SPACE_c5deef62fa6e488fa54f69f49381d5db`），但 **AIF/DCP 会话各自返回不同数据**（AIF 会话下树只有空的「我的目录/我的填报」，DCP 会话下有 3 个目录 9 篇文章）——数据按产品 context 隔离，同步配置需按产品分 profile。
- 服务端注入的 article JSON 含 `type / title / subjectId / updateTime / version / fileSize / filepath / annexs / secretLevel / download` 等字段，元数据够用，但**没有内容 hash**。

### 1.2 实测接口清单（2026-10-14，curl + 真实会话）

| 用途 | 接口 | 方法/参数 | 实测结果 |
|---|---|---|---|
| 目录树 | `/{root}/nonlogin/knowledge/space/findTree.htm` | POST `spaceId` | 200，subject 列表（`id/name/pid/type/isLeaf`） |
| 节点列表 | `/{root}/nonlogin/knowledge/space/findTreeByNodeId.htm` | POST `id, type, spaceId` | 200，**扁平全量**节点（subject + article 混排，article `isLeaf=true`） |
| 文章元数据 | `/{root}/nonlogin/knowledge/article/detail.htm?id=` | GET | 200，页面注入 `var article = {...}` JSON |
| 文件下载 | `/{root}/nonlogin/fileupload/downloadfile.htm?id=<fileId>.<ext>&path=.knowledge.space&name=<文件名>&mode=download` | GET | **200，9,067,613B docx**（article.filepath 字段直接给出该 URL） |
| 文件上传 | `/{root}/fileupload/uploadfile.htm;jsessionid=<JSESSIONID>` | POST multipart，字段 `Filedata`，`savePath=/knowledge/space` | 上传窗口页源码确认（未实际传，避免污染数据）；单文件上限该窗口配置 100MB |
| 上传后落库 | `/{root}/editorask/knowledge/article/fileSave.htm` | POST `data={files:[{annexId,annexName,annexType,annexSize,annexPath,annexMimeType}], spaceId, subjectId}` | knowledge.js 源码确认（一次最多 20 个文件），返回新文章 id |
| 替换文件 | `/{root}/editorask/knowledge/article/fileReplace.htm` | POST `{id: articleId, data:{files:[…]}}` | 详情页源码确认（**保文章 id 换文件**，正好对应"本地改了重新推"） |
| 在线预览 | `https://51yunwei.com.cn/preview/onlinePreview?url=<base64>` | GET | 详情页源码确认（kkFileView） |
| 目录 CRUD | `knowledge/subject/edit.htm?parentId=` / `swapOrder.htm` 等 | — | 页面线索，**未实测** |
| 删除/回收站 | `knowledge/space/deleteList.htm` / `article/draftList.htm` | — | 页面线索，**未实测** |

**实测空白（P0 必须补测，均为写操作所以本轮没碰用户数据）**：`fileSave`/`fileReplace`/`subject` 增删改/删除回收站/重名行为/配额上限/并发写。

### 1.3 对同步设计影响最大的三个平台事实

1. **无内容指纹**：远端只能拿 `updateTime + fileSize` 做变更判断，本地必须自己缓存上一次同步时的远端元数据快照当"基线"。
2. **无增量协议**：拉远端变更 = 全量 `findTreeByNodeId`（DCP 当前 12 节点无压力；数千文件的目录需要评估树接口性能与分页缺失问题）。
3. **会话按产品隔离 + 会话会过期**：同步引擎必须挂在现有 `auth::load_session` 上，401 → 暂停并提示重新登录；AIF/DCP 切换（`ops_product`）→ 切换同步 profile。

## 2. 技术方案

### 2.1 总体架构（贴合现有代码）

```
┌─ 前端（main.ts / mini.ts）────────────────────────────┐
│ 「我的」新增「网盘同步」分区：目录配对、启停、状态、冲突列表 │
│ 迷你条/标题栏：同步中↔已同步↔需登录 状态徽标              │
└──────────────┬───────────────────────────────┘
               │ invoke（新增命令，ACL 三处同步）
┌─ Rust ───────▼───────────────────────────────┐
│ sync.rs    同步引擎：扫描→对账→任务队列→执行→重试  │
│ sync_db.rs SQLite 同步状态库（.workbuddy 同目录）：    │
│            remote_snapshot / local_index / queue  │
│ http      复用 AppState.client + auth 会话          │
│ notify    目录监听（notify crate）本地即时上传        │
│ poller.rs 扩展：低频拉远端树做对账（对齐现有轮询）      │
└───────────────────────────────────────┘
```

新增 Rust 命令预计：`sync_pair_list / sync_pair_set / sync_pause / sync_now / sync_conflicts …`——**必须走 ACL 三处同步**（lib.rs 注册 + build.rs commands 数组 + capabilities `allow-<kebab-case>`），这是本项目踩过三次的铁律。

### 2.2 数据模型映射与状态机

| B/S 侧 | 本地侧 | 说明 |
|---|---|---|
| subject（目录） | 子目录 | 目录增删改走 subject 接口；本地根目录下的**散文件无 B/S 对应物** → 约定落到默认 subject（如「我的目录/客户端同步」），需产品确认 |
| FILE article | 文件 | `title`↔文件名（B/S 允许重名文章，本地不允许 → 以 articleId 建本地映射，文件名冲突加后缀并报冲突） |
| `updateTime + fileSize + version` | `mtime + size + hash` | 本地维护 `remote_snapshot`（上次同步时远端元数据）与 `local_index`（上次同步时本地状态），三方对比 |
| 无删除标记 | — | 远端删除 = 本轮对账时快照里有、现在没有 → 触发"确认后删除/移入本地保留区"策略 |

同步状态机（每文件）：`clean / local_new / local_modified / remote_new / remote_modified / conflict / deleting`。**冲突判定**：本地和远端都相对基线有变 → 默认保留双方（远端版下载为 `name(冲突 20261014).ext`），绝不静默覆盖。

### 2.3 同步流程

- **上行（本地→B/S）**：`notify` crate 监听目录（防抖 2~5s）+ 全量扫描兜底 → 新文件走 `uploadfile.htm → fileSave`；修改走 `fileReplace`（保 id，分享链接/消息引用不断）；改名走 article 改 title 接口（P0 补测）。
- **下行（B/S→本地）**：对账拉扁平树 → 与 `remote_snapshot` diff → 新/变文章走 `downloadfile.htm` 流式写临时文件 → 原子 rename。
- **节奏**：本地事件即时 + 远端对账随现有轮询低频（5~15min，可配）+ 标题栏刷新按钮强制 `sync_now`（对齐智能体列表刷新策略的实现模式）。
- **传输细节**：Rust reqwest 直接 multipart POST（不经 webview）；`;jsessionid=` 路径参数需原样保留；下载流式落盘避免大文件进内存；上传并发限 2、失败指数退避、客户端重启续跑队列（无断点续传协议，只能整文件重传——100MB 上限内可接受）。

### 2.4 阶段划分与工作量

| 阶段 | 内容 | 预估 | 验收 |
|---|---|---|---|
| P0 接口补测 | 用测试目录实测 fileSave/fileReplace/目录 CRUD/删除/重名/配额 | 0.5d | 接口矩阵表补全 |
| P1 只读镜像 | 拉树 + 下载 + 快照库 + 最小 UI（选择本地目录、进度） | 2~3d | B/S 传文件，本地自动出现 |
| P2 双向自动 | notify 上行 + 对账 diff + 冲突策略 + 暂停/恢复 + 状态徽标 | 4~6d | 两端改动自动收敛，冲突可解释 |
| P3 打磨 | 选择性同步、迷你条速览、限速、日志面板、异常自愈 | 3~5d | 日常可用 |

技术栈零新增重量级依赖：reqwest/tokio/sqlite 已有；新增 `notify`（目录监听）一个 crate。

## 3. 业务分析

### 3.1 AIF（运维）场景

| 场景 | 说明 |
|---|---|
| 运维报告自动归档 | 巡检报告、故障处置 docx 落本地工作目录 → 自动进「我的目录」，替代手工网页上传；B/S 端可分享给团队 |
| 多设备续作 | 公司机/笔记本经客户端同步同一份个人空间，出差现场改动回家自动收敛 |
| 与消息/待办联动 | 收到"请上传 XX 报告"消息 → 拖文件进同步目录即完成（长期可做消息卡片直达） |

### 3.2 DCP（一表通）场景

| 场景 | 说明 |
|---|---|
| 基层资料回传 | 采集的照片/扫描件/表格放目录即回传个人空间，基层人员零学习成本 |
| 模板分发（反向） | 上级在 B/S 放模板进个人空间 → 基层机器自动拉到本地 |
| ⚠️ COLLEXCEL 隔离 | 在线表格文章（填报产物）**不是 FILE**，同步引擎必须只处理 `type=FILE`，在线表格/富文本文章仅目录占位不落地 |

### 3.3 业务风险与约束

1. **网盘语义 vs 知识库语义**：个人空间本质是知识库——文件必须挂在目录下、title 可重复、无回收站语义确认、无配额接口。产品上要向用户说明"这是同步备份，不是完整网盘"。
2. **删除是高危语义**：本地删 → 远端删？建议首版"本地删仅解除同步（远端保留）"，远端删 → 本地移入保留区，P2 后期再开放真删（对齐用户"破坏性清理逐项确认"的一贯要求）。
3. **敏感数据**：article 有 `secretLevel` 字段（政企密级）；同步策略需可按密级过滤，本地缓存默认明文（与现有 B/S 下载行为一致，如需加密另立项）。
4. **多端并发**：网页端与客户端同时编辑同一文件必然冲突——冲突副本策略 + 时间戳提示是底线，不做自动合并。
5. **性能未知项**：树接口在数千文件时的响应、`uploadfile.htm` 是否限速/限并发——P0 用测试目录压一下。
